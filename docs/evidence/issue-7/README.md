# Slider preview and return

Ticket [#7](https://github.com/camilopaezz/reader-ldx/issues/7). Runtime verification completed for this bounded ticket. Results below describe actual Android behavior. The parent adoption gate remains failed until every required combined check passes; provisional interactions await owner review.

## Implementation and provisional policy

The bottom slider moves the live Readium page without saving it. Releasing a pointer leaves the preview open. Tapping the reading page commits that destination, closes controls, and records the pre-preview committed locator as the single Return target. Intermediate samples never become return targets. Cancel preview and Android Back restore the committed passage without changing that target.

A new slider commitment replaces the existing Return target. Return immediately moves to that target and swaps the current committed locator into the single target. Ordinary page, chapter, annotation-list, bookmark and diagnostic search-result navigation leave the target unchanged. If ordinary movement happens before Return, that current ordinary passage becomes the onward target only when the user presses Return. This is the two-position hypothesis for owner review; there is no deeper stack or separate Forward button.

A slider destination and its Return target save in one Room transaction. The additive reader database migration from version 1 to version 2 creates `slider_return` and preserves existing book rows. History is per imported book and device-local. Restart closes previews and restores the committed locator; warm resume retains the pending preview and its original source. Android Back dismisses transient UI and never traverses Return.

The slider uses 100 progression samples per reading-order resource. Percentage weights resources equally and is not a screen-page count or byte-accurate percentage. Preview honors navigator movement acceptance and checks requested progression against the actual paginated scrolling viewport, on the requested resource, before commitment. Requested locators, viewport geometry and rendered anchors are logged as `PREVIEW_SETTLED`. Commitment captures the actual visible paragraph anchor. Return preserves its target's exact publication-relative saved locator. The inherited precision remains paragraph/block-level.

## Runtime sequence

1. Preserve existing device data, install the version-2 APK and verify existing book rows remain. Import/open the Spanish fixture offline, choose a known chapter/paragraph source, and capture `COMMITTED` plus `SLIDER_STATE`.
2. Reveal controls and drag across several slider destinations without a page tap. Capture live pages during the pointer movement and prove the committed locator and Return target remain unchanged. Release and tap the reading page. Force-stop as soon as `SLIDER_COMMIT` is logged, relaunch, and capture the destination and target.
3. Return to the original source. Make a second committed slider operation and repeat Return/onward. Turn an ordinary page between those operations. Restart and record source, destination and Return state for each transition.
4. Preview and Cancel, then force-stop/relaunch. Repeat with Android Back. Preview and Home/resume; then force-stop/relaunch. Interrupt a long slider drag while the pointer is active, where device automation permits. Capture the original committed anchor in every restart.
5. Exercise Chapter, Search result and Bookmark style diagnostic jumps. These three minimal controls intentionally use the last reading-order resource as a common target; they exercise navigation categories without a production search index. Compare Return locator before and after. Also exercise actual bookmark/annotation-list navigation if a suitable record exists.
6. Sample font/margin reflow, lookup and a marked book-note overlay with existing reading-position commitment and Return state intact. Record any shared integration failures for the combined report.

No owner approval or passed combined gate is implied.

## Runtime failures and narrow corrections

The first resumed cross-resource drag loaded chapter2 but `navigator.go` put the page at progression .666872 rather than the requested .61. Requested point1505 lay outside viewport offset1645.714, width412, total scroll width2468. Strict settlement timed out and the app refused commitment without changing the durable source or Return. A separate selector Return loaded the correct chapter but remained at its beginning rather than showing `#p-2-14`; the captured sample did not reach its target. A separate raw timeout log was not retained for that selector sample. Earlier failed/intermediate captures remain in this directory, including `preview-B`, `corrected-preview` and `return-B`. The progression refusal and geometry were captured in tool output and are transcribed in [failure excerpts](runtime-failure-excerpts.txt).

The correction waits for the requested href, calls pinned Readium3.1.2 JavaScript `readium.scrollToPosition(progression)` or `readium.scrollToLocator(locator)`, then verifies actual viewport geometry for three samples or the selector's intersection with the viewport. The concrete bundled3.1.2 script exposes those functions. This is an app-owned workaround coupled to that engine version, not a universal EPUB or engine API guarantee. Final Return/cancel checks exercised the selector correction. Final live commitment exercised progression correction and captured current Readium progression plus first-visible block before the Room transaction.

The initial per-pointer-frame coroutine cancellation also starved navigator loads until release. The final worker conflates latest targets while allowing an active load to settle, then moves to the latest remaining target. Commitment freezes new samples and waits for that final target; cancellation blocks new samples and joins the worker before restoration. A timed-out earlier target leaves the preview unready and requires another move or Cancel, rather than silently committing an old destination. This failure path was not observed on the final run.

Read-only review found races around an in-flight ordinary Room write at preview start, a new drag during Cancel, and Return during typography recreation. The source now drains pending persistence under the shared mutex before capturing the preview/Return source, rechecks ordinary commitment under that mutex, blocks input during cancellation, and disables slider/Return during typography recreation. Those precise races were not reproduced on Android; source review is not runtime evidence for their interleavings.

An unexpected host emulator exit interrupted an earlier force-stop/relaunch attempt. `device_list` reported it unbooted. Reopening and updating the APK restored the same4-row source state; a transient `unknown package` probe during boot did not establish app data loss. The final live commitment/stop/restart was rerun successfully afterward. Initial migration captures contain5books while the resumed captures contain4 and no annotation records; this actor performed no clear/reset or deletion. The missing generic fixture between those epochs is unexplained. The earlier host interruption cannot pass the immediate-restart check; only the subsequent final result does.

CommitmentsA→B and B→C were recorded before the final selector-restoration change, with the same progression/Room commitment logic. Final source `9cd74c9` then exercised corrected Return/onward, cancellation, Back, warm resume, pointer interruption, diagnostics, and a complete fresh live commitment/Return/onward sequence. Earlier raw artifacts are background, not proof that those earlier APKs passed Return or live-preview requirements. `return-A` was a failed automation click using a stale reference and did not execute Return; it is not a passed app result.
